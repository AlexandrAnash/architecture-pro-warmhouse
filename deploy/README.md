# Деплой «Тёплого дома» на VPS

Как код едет от коммита до работающего сервера. Документ заодно — шпаргалка для защиты решения.

## Архитектура пайплайна (CI → CD)

```
push в deploy-branch
        │
   ┌────▼──────────────── build-push (матрица × 7 сервисов, GitHub-hosted runner) ──┐
   │  build образ → Trivy scan (гейт) → push в Yandex CR: :<sha> и :latest          │
   └────┬───────────────────────────────────────────────────────────────────────────┘
        │ needs: build-push  (стартует только если ВСЕ образы прошли)
   ┌────▼──────────────── deploy (SSH на VPS) ───────────────────────────────────────┐
   │  rsync compose+конфиги → docker login (stdin) → compose pull → up -d → logout   │
   │  → smoke-check                                                                   │
   └─────────────────────────────────────────────────────────────────────────────────┘
```

Ключевой принцип — **иммутабельный артефакт**: образ собирается один раз и по тегу
`= git SHA` едет на сервер. Никакой пересборки на проде; тот же образ, что проверен гейтом.

## Что где лежит

- `docker-compose.prod.yml` — прод-стек: тянет образы из `cr.yandex/${YC_REGISTRY_ID}/*:${IMAGE_TAG}`.
  Наружу открыты только gateway (`:8000`), фронты (`:8085`, `:8086`) и Web-STOMP (`:15674`).
  Postgres, AMQP (`5672`), management UI (`15672`), монолит и микросервисы — только внутренняя сеть.
- `.env.example` — референс, какие секреты завести в GitHub. **На сервере `.env` не создаётся.**

## Секреты (только GitHub Secrets, на сервере ничего не хранится)

| Secret | Назначение |
|---|---|
| `YC_REGISTRY_ID` | ID реестра Yandex CR |
| `YC_SA_JSON_KEY` | JSON-ключ сервис-аккаунта (docker login по stdin) |
| `POSTGRES_PASSWORD` | пароль БД (и в postgres, и в `DATABASE_URL`) |
| `RABBITMQ_USER` / `RABBITMQ_PASS` | учётка брокера |
| `VPS_HOST` / `VPS_USER` | адрес и деплой-юзер |
| `VPS_SSH_KEY` | приватный SSH-ключ (пара к публичному на сервере) |
| `VPS_SSH_KNOWN_HOSTS` | (опц.) пиннинг ключа хоста; без него — keyscan (TOFU) |

## Разовая настройка сервера

Секретов на сервере нет — нужен только Docker и пустая директория.

```bash
# 1. Docker + compose-plugin
curl -fsSL https://get.docker.com | sh

# 2. Деплой-юзер (публичный ключ уже добавлен в ~/.ssh/authorized_keys)
sudo useradd -m -s /bin/bash deploy
sudo usermod -aG docker deploy

# 3. Директория стека
sudo install -d -o deploy -g deploy /opt/smarthome
```

Логин в реестр и `.env` НЕ делаем руками — это берёт на себя CD на каждый деплой.

## Как деплоить

Просто `git push` в `deploy-branch`. CD сам: соберёт (уже собрано в build-push) → зайдёт по SSH
→ обновит стек по новому SHA → проверит health.

## Откат

Иммутабельные теги дают мгновенный откат — задеплоить предыдущий SHA:
```bash
ssh deploy@$VPS_HOST
cd /opt/smarthome
YC_REGISTRY_ID=<id> POSTGRES_PASSWORD=<...> IMAGE_TAG=<предыдущий_sha> \
  docker compose -f docker-compose.prod.yml up -d
```
(Из CI — перезапустить workflow на нужном коммите, либо `Re-run` предыдущего успешного деплоя.)

## Что сказать на собесе (обоснования и трейд-оффы)

- **Почему SSH-деплой, а не self-hosted runner:** для одиночного VPS SSH проще и безопаснее —
  раннер не крутится на бою с секретами репозитория; сервер «тупой», знает только про Docker.
  Self-hosted оправдан при закрытом наружу сервере, но тогда нужен ephemeral-раннер, отдельный
  непривилегированный юзер и запрет fork-PR.
- **Почему деплой по SHA, а не `:latest`:** воспроизводимость и откат. `:latest` — плавающий
  указатель, по нему нельзя понять, что именно крутится, и нельзя детерминированно откатиться.
- **Секреты:** в git нет; на сервере не хранятся; docker-логин по stdin + `logout` после pull.
  Компрометация сервера ≠ утечка секретов из репозитория.
- **Security-гейт до пуша:** Trivy с `exit-code 1` — уязвимый образ физически не попадёт в реестр
  и на прод. Осознанные исключения — в версионируемом `.trivyignore`.
- **Изоляция портов:** наружу только клиентские точки входа; БД/брокер/сервисы — внутренняя сеть.
- **Куда расти (честно про пределы):** единый reverse-proxy + TLS (Caddy/Traefik) вместо россыпи
  портов; секреты в Vault/облачном менеджере; healthcheck-и на всех сервисах и разворот стратегии
  на роллинг-апдейт/k8s, когда одного VPS перестанет хватать.
